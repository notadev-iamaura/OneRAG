# OneRAG 품질 평가 하네스 보강 계획

한국어 문서 조사 정책의 반복 평가, 실패 원문 추적, 후보 비교 및 로컬 개선 제안을 구현했다. `make rag-quality-smoke`와 `make rag-quality-local`로 실행한다. 아래는 11월 21일 기준 계획이며, 후속 한국어와 영어 평가에는 표본별 실측치를 공개했다. [로컬 실행 가이드](rag-growth-local.md) · [공개 평가 결과](rag-quality-results.md)

**첫 작업은 영역별 합격 판정기를 만드는 것이다.** 당시 독립 표본 H4에서 종합은 90.1점, 답변·근거는 72.9점이었다. 한국어에서는 답할 수 있는 24문항 중 17개에서 정답과 출처를 맞혔고, 답할 수 없는 12문항 중 5개를 올바르게 보류했다. 이 실행을 새 판정기에 넣었을 때 **‘전 영역 80점 미달’과 실패한 문항**을 함께 보여 주어야 한다. H4의 원문 및 문항별 기록은 당시 로컬 실행에 보관했다.

## 현재 하네스에서 이어 쓸 부분

- `make eval`은 파일에 기록된 질문·답변·문맥을 채점하고 평균 점수를 기준으로 종료한다. 현재 체크아웃에는 기본 입력 `data/eval_set.json`이 없다. 이 명령의 용도를 유지하고 제품에 질문을 보내는 평가에는 별도 진입점을 둔다. [Makefile](../../Makefile) · [기존 평가기](../../scripts/run_eval.py)
- 직전 실험에는 입력 해시, 문항 ID·분모 검사, 단일 검색과 에이전트의 대응 비교, 공개 원문 중복 검사가 있다. 당시 집계 코드에는 평가 체계 100점과 운영 80점이 상수로 들어 있었다. 다음 실행은 항목마다 이번 실행의 증거 또는 재사용한 증거의 출처를 요구한다. 후속 판정기는 채점 근거, 오류, 정책 간 대응 비교를 기록한다. [한국어 로컬 정책 판정기](../../scripts/rag_growth_gate.py) · [한국어·영어 표본 재채점기](../../scripts/rag_growth_public_gate.py)

## 구현 순서와 인수 기준

아래 기간은 담당자 1명 기준 구현 추정치다. 모델 실행과 근거 문장 검수 시간은 별도다. 표의 새 Make 명령은 구현 제안이다.

| 순서 | 작업·담당 역할 | 완료를 확인하는 방법 |
|---|---|---|
| **1. 판정기와 재현 기록 · 1~2일** | 평가 담당. 기존 채점식과 대응 비교를 정식 평가 스크립트로 옮긴다. 문항별 결과, 배점 항목별 증거, 코드·모델·프롬프트·데이터 해시를 하나의 실행 기록으로 연결한다. 커밋 후 작업 트리에 변경이 있으면 변경 내용의 해시도 남긴다. | 기존 증거를 연결하면 H4의 90.1점과 72.9점이 재현된다. 운영 증거를 제거하면 ‘미검증’, 문항 중복·누락이나 입력 해시 변경은 ‘입력 오류’가 된다. 과거와 같은 80점이 자동으로 부여되면 실패다. |
| **2. 답변과 근거 회귀 검사 · 2~3일** | RAG·QA 담당. 한국어는 같은 문서에서 인물·시점·수량·관계 중 하나만 바꾸어 답변 가능·불가 질문을 짝짓는다. 예를 들어 원문이 ‘피의자로 소환’만 설명하면 그 사실을 묻는 질문에는 답하고 ‘피고인으로 송치’를 전제한 질문에는 보류해야 한다. 영어는 연결 대상을 식별하는 문장과 요청한 사실을 입증하는 문장을 각각 표시한다. | 한국어는 짝의 양쪽 성공, 불필요한 보류, 근거 없는 답변을 각각 센다. 영어는 정답, 필수 문서 집합, 필수 문장 전체를 별도 채점한다. 원문을 그대로 인용하고도 다른 사람의 사실을 답한 사례가 의미 검사를 통과하면 실패다. 공개 원문으로 만든 고정 사례는 사람이 먼저 라벨을 검토하고 허용 가능한 대체 근거도 기록한다. |
| **3. PR 검사와 로컬 실행 연결 · 1~2일** | CI·백엔드 담당. PR용 `make rag-quality-smoke`는 고정 응답으로 판정기, REST·SSE·WebSocket·이력의 인용 계약, 단위와 취소·재시도 회귀를 확인한다. 후보용 `make rag-quality-local`은 동일한 로컬 모델과 인덱스로 기준 버전과 후보에 같은 질문을 보낸다. 기본 채팅, 한국어 문서 조사, 영어 단일 검색·에이전트를 각각 실행한다. | 합성 검사는 모델 없이 재현된다. 로컬 실행에는 실제 모델 호출, 답·인용, 도구 호출, 종료 사유, 토큰과 지연이 남는다. 오류·시간 초과도 분모에 넣는다. 후보 8개 중 인용 1개인 사례와 정상 보류의 빈 인용이 API부터 화면까지 유지되는지 확인한다. UI 변경 시에는 빌드된 화면에서 실제 인용을 열어 원문을 대조한다. |
| **4. 새 공개 표본으로 후보 채택 · 실행당 1회** | 평가·릴리스 담당. 기존 H4·H5·H6은 모두 회귀용으로 둔다. 다음 회차에는 개발셋과 질문·문서가 겹치지 않는 새 최종 표본과 재현 표본을 미리 예약한다. 기존 난이도와 분모를 유지하고, KorQuAD와 2WikiMultiHopQA에서도 미사용 문항을 따로 뽑아 전이 결과를 공개한다. | 실행 전 버전·표본·판정 기준을 고정한다. 결과를 열어 본 표본은 이후 노출된 것으로 표시한다. 후보 비교표에는 문항별 개선·악화와 95% 대응 신뢰구간을 남긴다. 전이 결과나 표본 간 방향이 다르면 일반화 판단에 그 차이를 명시한다. |

## 통과 기준

1. **PR 병합과 제품 품질 목표는 각각 판정한다.** PR은 변경한 계약과 기존 회귀 테스트를 통과해야 한다. 현재 기준 버전이 80점에 미달하므로 모든 PR에 80점을 강제하면 개선 작업 자체가 막힌다. ‘전 영역 80점 달성’ 표시는 후보 고정 후 새 최종·재현 표본 **각각**에서 반올림 전 다섯 점수의 최솟값이 80 이상일 때 부여한다. 두 표본 요구는 다음 회차에 제안하는 일반화 기준이다.
2. **기존 원점수 목표도 유지한다.** 표본별 한국어 정답·출처 동시 성공 ≥20/24, 올바른 보류와 빈 인용 ≥9/12, 영어 정답·필수 문서 동시 성공 ≥11/16, 단일 검색 대비 ≥10%p 향상, 평균 토큰 ≤1.5배다. 어느 항목이 부족한지 그대로 표시한다. 기본 채팅은 별도 지표로 답변 가능 8개와 불가 4개의 성공 건수를 같은 기준 버전과 비교한다. 필수 근거 문장 전체의 일치율도 별도로 공개한다. 신규 의미 검사의 배점 변경은 다음 평가 버전에서 사전 등록한다.
3. **증거 누락과 품질 미달을 구분한다.** 필수 실행의 분모·해시·증거가 없으면 ‘미검증’으로 두고 인증을 보류한다. 실행한 문항의 오류·잘못된 인용은 실패로 채점한다. 운영 영역은 기존 15점 배점을 유지한다. 로컬에서 검증 가능한 12점을 모두 입증하면 80점이다. 실제 배포 부하·비용 3점은 미측정으로 표시하고 배점 분모에 남긴다.

각 이터레이션은 개발셋에서 실패 원인을 하나 고르고, 변경 전후의 같은 문항을 대조한 뒤, 한국어 정답과 보류 또는 영어 근거와 토큰 사이의 손익을 기록하는 순서로 진행한다. 두 개발셋에서 채택 기준을 충족한 후보만 동결해 최종 평가로 넘긴다. 첫 구현의 인수 사례는 **H4의 90.1점 실행에서 답변·근거 미달을 잡는 것**과 **운영 증거가 빠진 실행에서 80점을 부여하지 않는 것**이다.
